## 2. 比較 Run の条件

- **Coding Model だけを GPU に置いた**（Memory Worker・Embedding・Reranker なし。Human の決定、Decision 0074 の背景の 2）。各 Run の開始前に GPU に他の Process がないことを確かめた（12 回すべて空き 97,231 MiB、自分の Process group なし）。
- vLLM 0.30.0、`--max-model-len 131072 --max-num-seqs 8 --gpu-memory-utilization 0.90`、Reasoning parser `qwen3`、Tool parser `qwen3_coder`。Sampling は各 Model の `generation_config` の既定（温度 0 ではない）。Weight は NVMe に Stage してから Load した。2 Model とも Load 後の VRAM は 87,078 MiB、KV Pool は 888k token。
- Harness・Prompt・Tool・Sandbox・Evaluator は 09-28 / 10-01 の Run と同じ（4 Task 並列、Task ごとに 60 step・45 分）。v2 のために足したのは、v2 の索引の読み込みと、部分点（acceptance の test case の通過率）の記録だけ。
- Dataset は `274ff00` の索引と、`/data/datasets/paw-seed-v2` の Hidden check を Run の前に固定した複製（`FROZEN`・`SHA256SUMS`）。6 回の Run はすべて同じ複製を使った。
- Host の安全の設定（Decision 0039 の 4）: `MAX_JOBS=4`、`FLASHINFER_NVCC_THREADS=1`、起動前の `MemAvailable` 32 GiB 以上、Run 中に 8 GiB を下回れば自分の Process group だけを止める Watchdog。Watchdog が止めたことはない。
- Run ごとに Server を起動し直した。Harness の Error・LLM の Error はすべての Run で 0。

### 予定から外れた点: Run の順番

予定は 2 Model を 1 回ずつ交互に（3.6 → 3.8 → 3.6 → 3.8 → 3.6 → 3.8）走らせることだった。実際の順番は次のとおり。

| 開始〜終了 | Model / Run |
| --- | --- |
| 10-05 15:22〜16:55 | Qwen3.6-27B-FP8 run1 |
| 10-05 16:55〜21:14 | Qwen3.8-27B-FP8 run2 |
| 10-05 21:14〜22:48 | Qwen3.6-27B-FP8 run2 |
| 10-05 22:48〜10-06 00:19 | Qwen3.6-27B-FP8 run3 |
| 10-06 11:27〜15:52 | Qwen3.8-27B-FP8 run1 |
| 10-06 15:52〜20:02 | Qwen3.8-27B-FP8 run3 |

- 原因は Run の Script（Repository の外の Harness）の Bug: Server を止める関数（`serve_lib.sh` の `stop_group`）が待ちの loop に global の変数 `i` を使い、呼び出し側（`run_198.sh`）の Run 番号の loop の変数を上書きした。このため Qwen3.8-27B-FP8 の 3 回の番がすべて run2 になり、1 回目で run2 を走らせ、2・3 回目は「run2 は済み」として飛ばした。Qwen3.6-27B-FP8 の 3 回は影響を受けていない。
- 直し方: `start_vllm`・`stop_group`・`one_run` の loop の変数を `local` にした。同じ Script で再開し、済んだ Run（`summary.json` がある Run）を飛ばして Qwen3.8-27B-FP8 の run1 と run3 を続けて走らせた。
- 影響: Qwen3.8-27B-FP8 の run1 と run3 は交互ではなく 10-06 に続けて走った。Dataset の複製・設定・Harness は同じで、GPU にはこの Run の Process だけがあった（開始前の確認も同じ）。Run どうしは状態を共有しない（Run ごとに Server を起動し直し、Task ごとに新しい Sandbox）。Qwen3.8-27B-FP8 の 3 回の Resolved は、10-05 の run2 と 10-06 の run1・run3 で同じ値（37）だった。

### Context の使い方

| Model | 1 step の出力 token（中央値） | Task ごとの Prompt の最大（中央値 / p90 / 最大） | Prompt が 100k token を超えた Task の回数 | Context 不足 |
| --- | ---: | ---: | ---: | ---: |
| Qwen3.6-27B-FP8 | 241 | 43k / 69k / 85k | 0 | 0 |
| Qwen3.8-27B-FP8 | 766 | 67k / 107k / 115k | 20 | 9 |

- **Context の上限は 2 Model で同じ**: vLLM の `--max-model-len 131072`、Harness の Prompt の上限 120,000 token（`MAX_CONTEXT`）、1 回の応答の `max_tokens` 16,384。2 Model とも Model 自体は 262,144 token に対応しているが、この Run では使っていない。
- 差は振る舞いから出た: Harness は Reasoning（`reasoning_content`）を会話の履歴に残すため、1 step あたり約 3 倍の出力を書く Qwen3.8-27B-FP8 の方が Prompt が早く伸びる。
- **制約**: 131k の設定では、Qwen3.8-27B-FP8 は長い Task で Context の余裕が小さい（147 回のうち 20 回が 100k を超えた）。Qwen3.8-27B-FP8 を将来 Deployment に使う場合は、古い Reasoning を履歴から落とすか、`max-model-len` を大きくすることを Context の大きさの設計で考える必要がある（この Run では試していない）。
- **KV の量（参考。選び方の結果は変えない）**: 2 Model は同じ構造（64 layer のうち full attention は 16 layer、KV head 4、head_dim 256、Model 自体の上限 262,144 token）で、1 token あたりの KV は同じ。この Run（単独、0.90）の KV Pool は 56.44 GiB = 888,125 token（vLLM の Log。131k の 6.78 倍）。
  - 共存時（Decision 0073 の 2、Main を 0.51）は Main の KV Pool が約 19.3 GiB・約 303k token で、Scheduler が Coding に許す予約は約 259k token（`kv_safety` 0.90 × Coding の上限 0.95）を最大 4 つの Agent で分ける。
  - KV の必要量の粗い見積もり（Task ごとの Prompt の最大の中央値 × 4 並列。応答の分（1 回最大 16k token）は含まない）: Qwen3.6-27B-FP8 は約 170k（43k × 4）で約 259k に収まるが、Qwen3.8-27B-FP8 は約 270k（67k × 4、p90 では約 430k）で超える。2〜3 並列なら収まる大きさ（実測していない）。262k の 1 Request は共存時の予約に収まらない。
  - ただし今の Scheduler（`HybridRuntime.run_node`）は、Node の開始時に最初の入力から見積もった token（と応答の予約 8,192）で Lease を 1 回取るだけで、Agent の会話が伸びても予約を更新しない。このため上の超過は Scheduler の Admission では止まらず、vLLM の KV Pool の中での待ち・Preemption として現れると見込まれる。Admission で並列を抑えるには、伸びていく Context を予約に反映する変更が要る（別の Issue）。
  - 対策の候補: 古い Reasoning を履歴から落とす、Main に GPU Memory を多く与える（Embedding / Reranker を CPU に置くなど）、並列の Agent を減らす。

### 読み方

- **Human の選び方**（Resolved@3 と平均の**両方**で Qwen3.8-27B-FP8 が 2 Task 以上多ければ Qwen3.8-27B-FP8）を当てはめると、平均の差は +4.0 で条件を満たすが、Resolved@3 の差は +1 で満たさない。**両方ではないため、Qwen3.6-27B-FP8 のまま**。
- **Human の決定（2026-10-07、Decision 0074 の承認時の決定）**: Human は上の規則の結果を示されたうえで、平均の差と揺れのなさを重く見て **Qwen3.8-27B-FP8 を Main に採用した**（Qwen3.6-27B-FP8 は次点）。共存時の確認 Run（0.51、paw-seed-v1）は Qwen3.8-27B-FP8 で行う。
- 事実として、Qwen3.8-27B-FP8 は 3 回とも同じ 37 Task を解き、Run の揺れがなかった（Qwen3.6-27B-FP8 は 32〜34 で、3 回とも解けたのは 30 Task）。一方で、所要と出力 token は約 2.8 倍だった。
- v1 の部分だけでは 2 Model の差は 0 で、差は新しい 25 Task で出た。v2 は「上位の Model の差を測れる」という目的は部分的に果たした（Resolved@3 で 1、平均で 4 の差）。
- 予備の Run の 3 Model は候補より弱く、新しい Task のうち 2 Model とも 3 回とも解けた Task は 16 ある。上位の差をさらに測るには、より難しい Task が要る（この Issue の範囲外）。
